# 05. Ресурсы, устойчивость и доверенные инварианты

## 1. Цена вычисления

Здесь MAC — одно умножение с накоплением; FLOPs≈2 MAC только для матричных операций. tanh, softmax, sorting, DSP, allocation и OS учитываются отдельно. Число параметров не равно числу операций.

Для q активных блоков:

\[
C_R(q)=Jq(2\chi bd+\chi b^2),\quad
C_R(n_b)=J(2\chi d^2+\chi bd).
\tag{R1}
\]

Вывод: в каждой ветви каждого блока A h и C z стоят по χbd; B u стоит χb². Bias/activation/усреднение — scalar ops. Расчёт не использует кэш C z; его введение снизит цену только после отдельного учёта storage и invalidation. Неактивные блоки не вычисляют ни A,C, ни B.

Encoder+memory-read для non-OS modality ширины f:

\[
C_{\rm enc/read}\le 2d^2+df+32d+2md+2M_{\max}m.
\tag{R2}
\]

Два md — query и W_r; две M m — scores и weighted values. Lookup текста не стоит Vd: это чтение d значений. OS использует один W_meta и f=0. Query s+g bounded, но не единичной infinity-norm; tanh всё равно ограничивает q.

Selector: C_mask=n_b(2d+4); wake — 32 MAC. Scalar sorting O(n_b log n_b) и сравнение budgets не входят в эти MAC. Финальные головы: C_head=d H_exec + d V·1_text. Пластичная и базовая success-readout требуют по Ad; они **дополнительны**: H_exec включает W_p и W_a, но P-readout надо прибавить Ad, если считаются success logits.

Итого консервативная оценка одного события:

\[
C_{\rm event}\le C_{\rm DSP}+C_{\rm enc/read}+C_{\rm mask}
+K[C_R(q)+d]+dH_{\rm exec}+Ad+1_{\rm text}Vd+32.
\tag{R3}
\]

Kd учитывает halt на каждом шаге. Если halt также включён в финальный H_exec, это консервативное повторное начисление, а не занижение. C_DSP — отдельно специфицированные MAC/операции preprocessing. Для receipt-event дополнительно резервируются запись key/value 2md, проекции, журнал и storage. Прогнозы всех голов не обязательно считаются одновременно.

При d=1024, всех блоках, K=8: только рекурренция 138 412 032 MAC/событие. Одна vocabulary-голова — 33 554 432 MAC/токен. Поэтому 100 аудиокадров/s и текстовая генерация не могут считаться «почти бесплатными». Разреженность, wake и разные K для кадров могут помочь; качество такого режима REQUIRES_DATA.

TTS DSP: I_GL итераций на F кадров длины N_fft дают O(I_GL F N_fft log N_fft) комплексных/вещественных FFT-операций плюс overlap-add. PCM samples/s, frames/s и text tokens/s — разные временные шкалы. Умножение стоимости одного кадра на число кадров обязательно.

## 2. RAM и storage

\[
RAM_{\rm peak}\le B_\Theta+B_P+B_M+B_{\rm ctx}+B_{\rm pending}
+B_{\rm DSP}+B_{\rm workspace}+B_{\rm OS}+B_{\rm staging}.
\tag{R4}
\]

К B_OS/B_staging отдельно прибавляются bounded canonical payload-store до16 MiB, trusted ledger headers до1 MiB, reactor/goal arrays и их WAL/staging copies. Размеры64/256 bytes в таблице — фиксированные refs, не inline predicate/prestate. Eviction/pinning правила заданы в01. Для полной памяти эти объекты нельзя пропускать.

Это верхняя оценка только если **каждый** член действительно ограничен backend-контрактом; формула с неизвестным B_OS сама по себе не доказательство численного RAM-cap.

Для опорной конфигурации:

| Объект | Формула | Значение |
|---|---|---:|
| FP16 Θ | 2PΘ | 110 640 878 bytes =105.515 MiB |
| P FP32 | 4Ad | 524 288 bytes =0.500 MiB |
| M FP16 keys+values, metadata 64 bytes | M_max(4m+64) | 2 359 296 bytes =2.250 MiB |
| Рабочий FIFO FP16 | 2N_ctx d | 524 288 bytes =0.500 MiB |
| ≤32 pending traces, 256 bytes metadata | 32(2d+256) | 73 728 bytes =0.0703 MiB |
| Audio PCM16, 10s | 2×16000×10 | 320 000 bytes |
| Две h и z FP32 | 12d | 12 288 bytes |
| Branch intermediates без градиентов | ≤4Jqχb | ≤32 768 bytes |

Таблица — полезная нагрузка, не PSS Android. Java/native objects, SIMD packing, dequant buffers, UI, GPU/DSP drivers, FFT, STFT, image buffers, verifier и mmap pages добавляются. INT8-файл может сосуществовать с распакованной FP16 копией: тогда учитывать обе. Не предполагать, что система Android даст весь физический RAM приложениям.

Checkpoint хранит (schema,modelDigest,graphDigest,s,P,β,Q,M,provenanceReferences,checksum/MAC); pending tickets и ν,e не восстанавливаются. При двух слотах нужен примерно 2×snapshotPayload плюс WAL и staging; snapshot Θ не дублируется, если manifest ссылается на отдельно защищённый файл. Disk-quota конечна: при исчерпании сохраняется безопасная остановка, а не бесконечный append.

## 3. Энергия и многокритериальная цель

\[
J_{\rm energy}=
\theta_{\rm mac}C_{\rm MAC}
+\theta_{\rm mem}B_{\rm moved}
+\theta_{\rm dsp}C_{\rm DSP}
+\theta_{\rm io}B_{\rm IO}
+P_{\rm idle}T_{\rm idle}
+J_{\rm screen}+J_{\rm OS}+J_{\rm control}.
\]

Коэффициенты могут зависеть от частоты, температуры, sparsity и backend; линейность — аппроксимация, проверяемая residual-анализом. Они не известны из handoff. Для полностью спящего neural path C_MAC=0, но J_control и фоновая ОС не равны нулю.

Метрика на фиксированном наборе **выданных** задач N:

\[
J_{\rm per-success}=
\begin{cases}J_{\rm total}/N_{\rm verified-success},&N_{\rm verified-success}>0,\\
+\infty,&N>0,\;N_{\rm verified-success}=0,\\
\mathrm{NA},&N=0.
\end{cases}
\]

Здесь +∞ — policy-конвенция для оценки, а не замена неопределённой дроби 0/0 в арифметике.

Hard constraints до оптимизации: права/STOP, минимальные success-rate и coverage по обязательным классам, максимальная false-success-rate, сроки, RAM, crash-rate. Отказы, уточнения и timeout включаются в denominator N и отдельные метрики. Уже удовлетворённые NOOP-цели выделяются в отдельный стратум, иначе можно искусственно улучшить успех.

После feasible-filter ищется Pareto-front (quality↑, coverage↑, joules↓, latency↓, RAM↓, regressions↓). Скаляризацию допускается применять только с опубликованными весами/единицами и без компенсации hard constraint. NCR-EVO и offline-training энергия учитываются отдельно и, если амортизируются, с явным сроком/числом устройств.

## 4. Доказательства

### T1. Типы и тотальность

База — валидный X0 из 01. Все входы либо входят в одно из ограниченных sum-types, либо INVALID. Размерности из 03 делают каждое произведение определённым; bounded queues имеют явный overflow-result. Таблица 02 выбирает первую применимую строку, с default INVALID. Обработка ограничена конечными K, длинами, квотами, timeout внешнего вызова как логическим исходом. Следовательно δ определена для всякого конечного события. Это не гарантирует завершение внешнего физического действия.

### T2. Ограниченность h,s,β,P

tanh даёт z,F_j∈[−1,1]. h0 — выпуклая комбинация s,z. D1 в активном блоке — выпуклая комбинация h,F, в остальных — прежнее h. Индукция по k,t даёт ||h||∞,||s||∞≤1. Sigmoid β∈[0,1]. Проекция строки P на closed L2 ball даёт ||P_a||2≤pmax; по индукции ||P||F≤sqrt(A)pmax. Memory values после tanh также bounded. Ограниченность не равна сходимости.

### T3. Контракция фиксированного F

Предпосылки: z,Θ,Γ фиксированы; norms из 03; идеальная арифметика. tanh 1-Lipschitz, поэтому

\[
\|F_j(h,z)-F_j(\tilde h,z)\|_\infty
\le J^{-1}\sum_l\|B_{lj}\|_\infty\|A_{lj}\|_\infty
\|h-\tilde h\|_\infty
\le\gamma\|h-\tilde h\|_\infty.
\]

Взять максимум по блокам: F — γ-contraction на полном замкнутом кубе. Куб complete; итерация F имеет единственную fixed point h*. Для полной leaky-маски:

\[
\|T(h)-T(\tilde h)\|_\infty
\le[1-\alpha(1-\gamma)]\|h-\tilde h\|_\infty=c\|h-\tilde h\|_\infty,\quad c<1.
\]

При частичной маске один шаг может иметь Lipschitz=1. Если **каждый блок обновлён за F_cov шагов**, все используют тот же F и одни и те же маски в сравниваемых траекториях, то за покрытие:

\[
\|h^{k+F_{\rm cov}}-h^*\|_\infty\le c\|h^k-h^*\|_\infty.
\]

Доказательство: максимальная ошибка не растёт; при обновлении блока его ошибка ≤c E_start, и сохраняется ≤c E_start при дальнейших обновлениях до конца покрытия. После покрытия все блоки удовлетворяют оценке.

Если блок никогда не включается, полная контракция не следует. Если маски выбираются разными h, вход z меняется, меняются веса/структура или отсутствует fairness — эта теорема неприменима. Поэтому bounded finite-depth runtime не рекламируется как сходящийся ко всему правильному поведению.

При возмущении округления ≤ε_num на шаг безопасная sweep-оценка:
E_next≤c E_start+F_cov ε_num, limsup E≤F_cov ε_num/(1−c). Это верхняя граница чувствительности при предпосылках, не bound task-error. Для полного residual r=h−F(h):
||h−h*||∞≤||r||∞/(1−γ). Sparse residual отдельных блоков такого сертификата не даёт.

### T4. Жёсткий вычислительный бюджет

Лимиты — вектор неотрицательных квот. В начале reserve c_final+c_abort+c_control. Перед каждым primitive с сертифицированной верхней стоимостью c_i исполнение допустимо только если c_i+reserve≤remaining покомпонентно. Затем remaining'=remaining−c_i. Индукция даёт Σc_i+reserve≤B_initial. Маски и halt выбирают только из допустимых вариантов, поэтому обучаемые веса не могут нарушить этот арифметический лимит.

Если оценка c_i занижена, не учтён selector или ОС выделяет неожиданную память, численное утверждение не доказано. Поэтому контрольные расходы отделены от neural budget, и при B_work=0 STOP всё ещё обслуживается. Конечный K гарантирует конечное число neural ops, но не hard real-time Android.

### T5. Изоляция полномочий и STOP

Предпосылки A_cap: только доверенная граница владеет capabilities; mutable graph не может писать T/L, создавать dispatch-системные вызовы вне gate или менять verifier; trusted runtime и ОС корректны. Каждый OS-dispatch имеет единственную точку linearization с проверкой актуальных условий. По индукции над переходами ни одна операция δ mutable-части не создаёт capability; dispatch появляется только в allowed-ветви trusted gate. Следовательно любые Θ,P,ошибки модели не расширяют полномочия.

STOP, linearized до dispatch, запрещает его. Если dispatch уже произошёл, физическое последствие может завершиться после STOP. Обещание «STOP мгновенно отменит всё в мире» REJECTED. Реальный bound STOP-latency требует ОС/планировщика и независимого приоритета, не формулы весов.

Это не гарантия от kernel exploit/скомпрометированной ОС. Plain Python object с underscore-полями не удовлетворяет A_cap против враждебного кода.

### T6. Stale/replay/rollback не обучают

Предпосылки A_gen, A_cap, транзакционная фиксация A_tx. Learn-ветвь требует совпадения ι с active ν,e,v,goal,digest и unused. STOP увеличивает e; restore/restart сначала меняет ν независимо от snapshot. Поэтому старая ι не проходит equality. Receipt помечается used в той же транзакции, что P', поэтому повтор не может примениться второй раз. Восстановление старого P не возвращает старое ν и не открывает ticket.

Без защищённого от rollback ν или atomically updated ledger теорема неверна; контрпример PR #3 — в 07.

### T7. Persistence и corruption

A_fs: запись staging → flush(data) → атомарная смена указателя/rename → flush(directory), с известными durability-гарантиями носителя. A_auth: model manifest и snapshot аутентифицируются доверенным ключом или защищённой hash-reference; plain SHA детектирует случайную порчу, но не подделку.

При двух слотах и A_fs читатель либо видит старый завершённый слот, либо новый; недописанный staging не становится текущим. Полная проверка schema, lengths, norms и digest до загрузки исключает частичную замену состояния. A_gen всё равно создаёт новую generation. При провале обоих слотов — immutable baseline s=P=0, память карантинируется, STOP=true. Если trust-anchor повреждён — SAFE_MODE.

Если storage не гарантирует atomic/durable commit, это остаётся требованием к будущему backend, а не уже доказанным Android-фактом. Сам checksum не доказывает свежесть корректно подписанного старого файла.

### T8. Контрольное качество

На фиксированном конечном наборе deterministic oracle, принимая только покомпонентное улучшение/равенство, получаем Q_control(new)≥Q_control(old) по определению допуска и транзитивности. На будущих задачах, при шумных оценках или смене распределения монотонность не следует. Counterexample двух задач и одного общего параметра — в 07.

## 5. Crash loops, idle и регенерация

Одна цель допускает ≤3 неуспешных auto-attempts на неизменной preconditionVersion; далее CLARIFY/SAFE_MODE. Retry-backoff и общий work-token budget не могут отменяться повтором того же наблюдения. Это предотвращает неограниченные внутренние повторы на данной версии задачи, но не доказывает отсутствие бесконечного потока новых внешних задач.

Три разных понятия:

1. File recovery — получить прежние байты из валидного снимка.
2. State reconstruction — восстановить вычислимое состояние из независимого журнала.
3. Functional regeneration — найти **другой** алгоритм/структуру, выполняющий утраченную функцию по контракту.

Первые два не увеличивают интеллект. Третий требует NCR-EVO/equivalence obligations и новых испытаний; если утрачена вся информация, восстановление произвольной функции невозможно.
