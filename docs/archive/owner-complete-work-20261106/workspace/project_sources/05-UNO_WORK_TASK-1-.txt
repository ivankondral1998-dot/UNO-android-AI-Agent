# ЗАДАНИЕ CHATGPT WORK — UNO / UNOVYRA
## Перерасчёт минимального каркаса единого нейронного организма на бумаге

**Дата:** 03.11.2026  
**Режим:** самостоятельная предкодовая математическая и системная инженерия, с независимым критическим аудитом  
**Итог:** единая бумажная спецификация для обсуждения и возможного утверждения владельцем; **не код и не APK**  
**Приоритет:** первоначальные требования владельца → проверенные исходные расчёты → адресные исправления → исполняемый каркас только как НЕнормативный пример.

## 0. Прочитай прежде всего

Владелец не поручал строить девять самостоятельных модулей, переносить архитектуру Jarvis или назначать телефону модель с 55 млн параметров. Цель — **новый, полностью автономный, локальный, коммерчески пригодный Android AI-агент UNO**, по принципу **одного нейронного организма**: общая обучаемая нейронная организация, единое состояние, память, пластичность, адаптивная активация, решение и опыт. Android — первое физическое тело (Samsung Galaxy A52, Android 14), не предел концепции. Число файлов/классов не равно числу интеллектуальных модулей. Системные границы Android/доверия не являются вторым интеллектом.

**Критически важно:** пользователь с самого начала хотел сначала довести всё, что можно, до согласованного бумажного чертежа, чтобы будущие ИИ-разработчики не теряли контекст и не выдумывали устройство UNO. Только ПОСЛЕ обсуждения и утверждения бумажного каркаса следует переходить к производственному коду, обучению весов и Android APK.

## 2. Неприкосновенные ограничения

- **Один интеллект:** один общий обучаемый оператор/нейронная организация с общим состоянием, а не ансамбль отдельных мозгов, отдельная LLM для планирования, отдельная модель «памяти», девять постоянно исполняемых интеллектуальных модулей, BrainPort/Bridge/Orchestrator.
- **Минимум независимых частей:** минимизировать постоянно работающие процессы, службы, дублирование весов, преобразования и посредников. При этом не объявлять «один файл/один Android-процесс» самоцелью, если безопасность требует изоляции. Показать число действительно необходимых *доменов исполнения и доверия*, и почему меньше нельзя без нарушения условий.
- **Полный функциональный замысел:** речь, текст, экран, сенсоры, память, целеполагание, решения, адаптация, безопасные Android-действия, обратная связь. Не заменять полноценный организм 5-кнопочным классификатором ради малого веса.
- **Режим покоя:** тяжёлая нейросеть не обязана постоянно работать; event-driven активация, реальный пропуск ненужных вычислений. Микрофон/VAD/WAKE и Android foreground restrictions всё равно потребляют ресурсы и должны быть оплачены.
- **100% локальный runtime:** без облачных LLM, API, OAuth, удалённой памяти, сетевых fallback и скрытых сетевых провайдеров файлов.
- **Отдельная доверенная граница:** owner-auth, permissions, consent, STOP/epoch, native effect verification и долговечный журнал не могут быть переписаны нейросетью или NCR-EVO. `Memory ≠ Permission`, `History ≠ Current State`, `Proposal ≠ Verified Effect`.
- **Новые веса и новый продукт**, Jarvis — лишь минимальный донор проверенных технических приёмов; CELL/PMB, Bodycam, MLBB, NetworkClient не включать в UNO.
- **Никакого заранее назначенного размера:** B2 `d=1024`, `V=32768`, `55,451,639` параметров — контрольный расчётный кандидат, **не решение для телефона**. Число параметров само по себе не определяет тепло и батарею; главны полные MAC/s, bandwidth, пиковая PSS, latency, idle W и joules/issued task при достаточном качестве.
- **В этой задаче:** не писать/переписывать производственный код, не обучать веса, не запускать Android сборку и APK, не изменять репозитории, не удалять файлы, не выполнять GitHub Actions, merge, force push, push, публикацию или перенос секретов. Допустимы только независимые вычислительные скрипты/таблицы для *проверки арифметики* (не разработка агента). Исходники сохранить неизменными.

## 3. Основная инженерная работа — сделать самостоятельно

### A. Восстановить оригинальную архитектурную задачу

Свести ранние формулировки владельца в таблицу: **прямая цитата/источник → обязательное требование → математический контракт → что в R5.3 соответствует → противоречие/пробел → предлагаемое минимальное решение**. Особенно проверить различие `один интеллект` и `одно ПО/один процесс`, `минимальные органы` и `минимальные функции`, `новая нейронная структура` и `замена старых весов`. Не изобретать текст недоступных разговоров.

### B. Вывести действительно минимальный бумажный каркас

Построить **ровно один** end-to-end граф работы организма:

`типизированное событие → допуск/бюджет → общее представление → единое состояние/память → повторяемый F с активными связями → предложение решения → доверенная Android-проверка/исполнение/доказательство → ограниченное обновление опыта и P → покой`.

Указать отдельно:
- какие переменные реально составляют единое нейронное состояние (`Θ, s, g, β, M_memory, P, G_effective`, budget и т. д.);
- какие функции — **операции внутри одного вычислителя**, а какие — неизбежные внешние Android API/доверенные функции;
- минимальный набор типов сообщений на единственной границе (`Event`, `Proposal`, `Evidence`, `STOP` и, если строго нужно, другие), полные поля/размеры/версии/отказ;
- есть ли необходимость в отдельном ОС-процессе для sandbox без появления второго AI; число живущих служб в foreground/background;
- как восприятие речи/изображения/сенсоров выполняется **одним** ядром без скрытых параллельных LLM;
- цикл времени/активации и backpressure, чтобы wake/sensor/входы не запускали тяжёлый F в бесконечном polling;
- как обеспечить точные записи памяти без второго интеллектуального модуля.

Не называть выходные головы/тензоры/классы исходного кода девятью независимыми модулями. Если предлагается 2–3 runtime-части, объяснить *почему они физически/безопасностно обязательны*, а не просто показать названия.

### C. Разрешить главную коллизию графа

Ранняя идея `G_t=(V_t,E_t)` допускает развивающиеся нейроноподобные связи; действующая B2/R5.3 во время runtime держит slow `Θ` и топологию фиксированными, меняя блоковые маски, память, состояние и fast `P`.

Строго различить и рассчитать три механизма: **(1)** изменение активных связей `E_effective(t)` без смены топологии; **(2)** пластичность весов на подтверждённых исходах; **(3)** реальное добавление/удаление рёбер, нейронов или матриц. Для каждого: инварианты, правило изменения, ресурс, возможность обучения, сохранение компетенций, миграция, доверенная граница и способ опровержения. Сопоставить безопасный минимальный baseline (1)+(2) с вариантом runtime rewiring (3) и лабораторной версионированной заменой модели. Выбрать аргументированный кандидат на обсуждение, **не объявлять owner-approved**.

### D. Пересчитать геометрию и мобильную цену, а не назначать 55 млн

Взять оригинальную W2/W3 и полный список тензоров; независимо проверить 198 shapes/counts и fixed-zero coordinates для B2. Построить **параметрическое семейство кандидатов** с вариациями `d`, `V`, `b`, `J`, `χ`, `m_mem`, условной глубины `K`, масок и возможного low-rank подхода. В любом изменённом варианте пересчитать **все** tensor shapes, trainable/free, frozen, quant ABI, градиентные пути, вывод текста/ASR/TTS и перенос состояния. Не считать уменьшение словаря бесплатным для русского или качества; обеспечить byte fallback, EOS и schema tokens.

Представить сравнимую таблицу как минимум: B2-512/B2-1024 для воспроизведения исходных цифр, и разумные **более компактные варианты как новые гипотезы**. Не обещать, что они интеллектуально достаточны. `E_text = V*d` выделить особо как основного потребителя параметров. Для каждого варианта оценить:
- числа параметров, веса INT8/FP16, workspace, память ключей/значений, peak RAM с неизвестным backend overhead;
- MAC на TEXT token, AUDIO frame/s (включая WAKE и полный тракт), 256 IMAGE patches, SENSOR, memory retrieval и целый цикл proposal/readback;
- стоимость selector/mask и факт пропуска kernels, memory-bandwidth lower bound, лимиты нагрева/очередей/idle;
- зависимость будущего качества от данных и архитектуры, что **не выводится** из бумаги;
- explicit fallback: если маленькая конфигурация не проходит качество, расширять точечно, а не обрезать функции.

Не делать ложных численных заявлений о мощности A52 или сравнении параметров с «мобильной версией OpenAI» без достоверных данных. Реальный размер/энергия и качество только после измерений и обучения.

### E. Полная согласованная математика единого цикла

Проверить и написать единую формальную модель с определениями и единицами: исходный `O_t`, `S1–S7`, W2/W3, `L3a/L4/L5`, `P1–P3`, R5/R6, типы памяти, таймеры, отчёты `TRUE/FALSE/UNKNOWN/MAY_HAVE_EXECUTED`, consent/STOP, цикла сна/пробуждения и бюджета. Для всех подсистем — вход, выход, связь с единой F, время жизни, ограничения, невозможные случаи, оракул проверки. Отдельно закрыть индексы `m_mem` vs `n_task`: число проверочных направлений **не равно** числу классов обучения; пересекающиеся задачи получают однозначную первичную обучающую метку или объявленную другую математическую схему.

Устойчивость: различать boundedness, fixed-input contraction, adaptive hard mask discontinuity и global agent stability; дать доказательства и контрпримеры. Обучение: supervised/BPTT/CTC и score-gradient для sampled decisions, frozen offline P=0, censored outcomes, отсутствие данных/прав, retention/forgetting и честный UNKNOWN. Для вейк-слова не заменять акустический детектор metadata head `1×32`. Android trust, UI side effects, точность native-readback и strict offline — без подмены предсказания моделью системного разрешения.

### F. Проверить пригодность архитектуры ДО кода

Подготовить **бумажные проверочные векторы**, инварианты и негативные примеры для каждого интерфейса; список независимых тестов будущего эталона/Android, но **не реализовывать приложение**. Обязательные контрпримеры: недопущенная WAKE команда, невозможное/пустое sensor reading, противоположные записи памяти, stale consent/STOP после dispatch, частичное выполнение, missing outcome, delayed readback, mask discontinuity, full-text decoder costs, low-power idle, reboot/ABA, long context, забывание после P, изменение ABI при изменении V/d.

### G. Повторный независимый аудит и честное решение G4

Сделать минимум **три разных прохода**: (1) формулы/размерности/ресурсы с независимыми таблицами; (2) враждебные контрпримеры и безопасность; (3) интеграционная проверка требований владельца и минимальности топологии. Для каждого утверждения метка `PROVEN_CONDITIONAL`, `ARITHMETIC_PASS`, `SPECIFIED_UNTESTED`, `OPEN`, `FAIL`, `REQUIRES_DATA` с точной предпосылкой и ссылкой. Не считать integrity ZIP и число PASS доказательством интеллекта. Отдельный adversarial audit скрипта (изменение знака L3a, класса обучения, shape) — только если реально написан и запущен. Никогда не утверждать «100%», «всё доказано», «Android работает» без испытаний.
