# UNO — сравнительный эксперимент с типами весов (07.11.2026)

**Результат: исследовательский host-тест завершён, продуктовые веса НЕ выбраны.** Это НЕ полный UNO, НЕ испытание Samsung A52, НЕ измерение энергии и НЕ демонстрация общего интеллекта.

## Кратко

Новые имена + новые формулировки, точный **адресат и тип сообщения** одновременно, по **160 одинаковых запросов на каждый из трёх запусков**:

| Подтип весового слоя | seed 20261107 | seed 20261108 | seed 20261109 | Среднее |
|---|---:|---:|---:|---:|
| Плотный FP32 (64×64) | 111/160 | 106/160 | 98/160 | **65,63%** |
| Факторизованный FP32 (64×16 и 16×64) | 109/160 | 97/160 | 83/160 | **60,21%** |
| Троичный STE в прямом проходе (64×64, latent FP32) | 109/160 | 118/160 | 104/160 | **68,96%** |
| Простое правило из лексики исходного запроса | 160/160 | то же | то же | **100%** |

Для знакомых формулировок новые имена копируются точно у всех трёх моделей: 160/160. На новых формулировках результаты хуже — проблема в понимании, КОМУ адресовано действие. Копирование имени выполняется **детерминированно по заранее предоставленным границам двух кандидатов**, а не свободной генерацией слов нейросетью. Поэтому результаты НЕ проверяют способность UNO самостоятельно находить адресатов в произвольном тексте.

## Что реально сделано

1. Сначала сгенерированы и закреплены SHA-256 корпуса: 3000 синтетических обучающих запросов, 400 проверочных и пять тестовых групп по 160 запросов (800 уникальных). Каждый тестовый набор содержит 80/80 целей A/B; пересечений с обучением нет; новые имена состоят только из известных букв. Данные созданы самим кодом, чужие материалы не использованы.
2. В протоколе до начала обучения закреплены три типа FF-матриц, общие входные данные, 400 обновлений на модель, batch64, одинаковый AdamW, одинаковые 3 действия и основной тест.
3. Первая предварительная серия (`src/train_eval.py`, результаты и checkpoints без префикса `v2_`) оказалась **методически дефектной**: последовательность инициализации разошлась, и общие веса на старте различались между архитектурами. Она сохранена как ошибочный материал; выводы по ней не делать.
4. До повторной серии добавлен `PROTOCOL_AMENDMENT_V2.json` с SHA-256: **2e707643001c44023099c7e813e76a9fbb980b7e3db6791da2677b473f5bcda1**. Для каждого seed в трёх моделях теперь ПОБАЙТОВО одинаковые начальные веса общего encoder, GRU, общего преобразования и выходных голов. Новая серия: 3 seed × 3 вида весов × 400 обновлений, сохранила исходный корпус и конфигурацию.
5. В отдельной чистой копии ещё раз обучены все три варианта на seed 20261107; **все три повторные checkpoint и файлы предсказаний побайтово совпали** с исходными (`results/CLEAN_TRAINING_REPLAY.json`). Первая автоматизированная попытка этой проверки не завершилась; затем успешные отдельные команды с кодом 0 и побайтовой сверкой сохранили её результат.
6. Сохранены 9 реальных checkpoint формата `safetensors`, раздельные stdout, stderr, exitcode и 9 наборов текстовых предсказаний. Отдельный `src/audit_replay.py` заново загрузил checkpoint и **полностью сверил 7200 предсказаний** с сохранёнными результатами. Пять тестовых групп ×160×9 =7200. Результат `REPLAY_AUDIT.json`, завершение 0.

## Честность вычислительного сравнения

Это однотипные маленькие модели: одинаковые символьные embedding32 и двунаправленная GRU32+32, общая проекция и две выходные головы. **Меняется только один 64×64 FF-блок**: плотный / факторизованный rank16 / искусственно тернаризованный в forward. Здесь **не** сравниваются целиком B2, C256, C256R32, UNO-N0 и HSR. Соответственно, тест НЕ может выбрать лучший полный UNO-оператор.

| Показатель | Dense | Factor | Ternary |
|---|---:|---:|---:|
| Обучаемых параметров всего | 30 821 | 28 773 | 30 821 |
| Параметров в отличающемся блоке | 4 160 | 2 112 | 4 160 |
| Аналитические MAC на всей train-последовательности по условной формуле | 14 061 711 360 | 14 009 282 560 | 14 061 711 360 |
| Снижение MAC Factor относительно Dense | — | **0,373%** | — |
| Размер checkpoint (`safetensors`, bytes) | 124 612 | 116 508 | 124 612 |

Общие GRU и другие операции доминируют: 50% экономии в одном FF-блоке превращаются всего в ~0,37% снижения *теоретических* MAC всей этой архитектуры. Это НЕ число для готового UNO. Обратный проход, квантование и системные накладные расходы в формуле MAC **не учтены**. 400 обновлений и одинаковые minibatch на каждом seed; реальное CPU-время логируется, но это не равная энергия. Все хранимые tensor — FP32, в том числе latent ternary. **INT8-инференс и аппаратная тернарная арифметика не реализованы.**

## Реальные риски

- Новые формулировки снизили точность, при этом некоторые ошибочные адресаты имели уверенность сети ≥90%. Поэтому нельзя выполнять Android-действия только на основании ответа такой модели. Системная authority, STOP, consent и native readback — отдельная обязательная граница.
- Лексический baseline с известной грамматикой синтетических запросов дал 100%; это показатель слабости задачи/модели, **не** доказательство универсальности regex в живой речи.
- Один синтетический фиксированный корпус, публичная генерация, 3 seed. После предварительной серии V1 тестовые результаты уже были просмотрены, поэтому V2 — исправленная репликация, **не** слепая проверка на свежем скрытом тесте. Лексический baseline был дописан после первого ознакомления с грамматикой, до V2; он не является независимой недоступной модели контрольной выборкой. Нет внешнего закрытого holdout или естественных пользовательских сообщений. Интервалы статистической надёжности вне этого распределения не оцениваются.
- Протокол и данные зафиксированы до расчётов; **исходники Python не были отдельно закреплены по SHA до самого первого запуска**. Теперь их хеши включены в конечный манифест. Это ограничение provenance, а не повод заявлять полноценную preregistration.
- Никакие измерения энергии, тепла, RAM в Android, забывания и обучения на проверенных последствиях здесь НЕ проводились.

## Как проверить

На машине с Python 3, PyTorch CPU, NumPy и safetensors из этого каталога:

```bash
python src/audit_replay.py
python src/rule_baselines.py
python verify_release.py
```

Для **нового запуска обучения** (создаёт и перезаписывает свои checkpoint и results — использовать только в отдельной копии пакета):

```bash
sh run_v2_portable.sh
```

Данные и checkpoints не изменяются при запуске `audit_replay.py`. Полные логи находятся в `logs/`, исходники `src/`, матрицы `checkpoints/`, выводы `results/`.

**Решение:** пока **НЕ ВЫБИРАТЬ** тип весов UNO по этому исследованию. Если устройство не может надёжно определить конкретного адресата, нужен доверенный слой извлечения и подтверждения сущностей, а не попытка угадать имя с высокой уверенностью. Дальнейшее сравнение полного C256 / C256R32 / ternary / N0 на полезных навыках и A52 — отдельная задача с новым протоколом, не результат этого теста.
