# UNO · языковой тренер для Windows CPU · FIX03

Переход существующего F с текстовым входом и выходом. Конфигурация d512, b64, χ4, J2, фиксированные 8 блоков и K1, α=ρ=0,5. Весов для старта не требуется.

## Windows

1. Установите Python 3.12 x64. Распакуйте ZIP в новый локальный каталог. Положите рядом исходный `UNO_RU_COMMERCIAL_CORPUS_20261126.zip` из закрытого Google Drive. Его SHA-256 — `dd6b529194ac6833bb843f4197b75636536c53bafd29f28faa5a151a60726422`.
2. Запустите `INSTALL.cmd`. Он устанавливает зафиксированные CPU-зависимости в локальное окружение.
3. Запустите LibreHardwareMonitor **0.9.6** от администратора. В Options включите **Log Sensors**, установите **Logging Interval = 1 second** (желательно ежедневная ротация). Оставьте программу открытой. CSV должен создаваться в папке LibreHardwareMonitor. Запустите CMD от администратора, перейдите в каталог тренера и выполните `CHECK.cmd`. Он выполняет короткие синтетические тесты, проверяет корпус, допуск по аппаратной телеметрии и профиль одного синтетического шага d512.
4. После успешного CHECK — отдельная короткая аппаратная проба с разрешения владельца. Длительный запуск пока не допущен. Ниже команды для будущего согласованного запуска:

   ```bat
   START_TRAINING.cmd --steps 2000 --threads 2 --warmup 16 --backend analytic --seconds 1800
   RESUME_TRAINING.cmd --steps 2000 --threads 2 --warmup 16 --backend analytic --seconds 1800
   TEST_MODEL.cmd --prompt "В тихий вечер" --tokens 64 --validation-targets 512
   TEST_MODEL.cmd --validation-targets 112994 --export text_f.uno
   ```

   По умолчанию checkpoint находится в `uno_cpu_run\latest.uno`. Для отдельного эксперимента задайте `--output` с новым каталогом. Шаги, число потоков, warmup, backend, исходники, корпус и среда при resume должны совпадать. FIX03 не принимает checkpoint другой версии исходников без отдельной миграции. У `--seconds` для train/resume есть независимый внешний предел `seconds+60` на старт/сохранение; он прекращает зависший запуск. Предел секунд относится к одному вызову. Не меняйте бюджет шагов посреди эксперимента: от него зависит LR. Продолжение остановленного запуска выполняется с теми же аргументами. При Ctrl+C или аварии восстанавливается последний записанный шаг. Лог сообщает текущий шаг и отдельно `saved_step`; при аварии восстанавливается последний сохранённый шаг, а не последний показанный.

## Температура и ресурсы

FIX03 читает локальный CSV LibreHardwareMonitor 0.9.6 по каталогу обнаруженного запущенного процесса. Проверяются идентификатор и имя именно датчика CPU, число, время строки и время изменения файла (до 5 секунд), единственность работающего экземпляра LHM и свежесть относительно времени его запуска. WMI и сетевой сервер не используются. При отсутствии свежих данных допуск закрыт. В отчёте Acer обнаружен `/amdcpu/0/temperature/2`, `Core (Tctl/Tdie)`. Фактический CSV этого ноутбука ещё не проверен.

Все штатные CHECK/START/RESUME/TEST запускаются через отдельный контролирующий процесс `supervise.py`. Он проверяет пороги независимо от окна обучения: 85 °C, 95% общей загрузки CPU, суммарный RSS контролируемого дерева от 4096 МиБ, доступная RAM до 1536 МиБ, свободный диск менее 512 МиБ. При нарушении завершает рабочий процесс. До первого допуска вычислительный процесс не начинает работу. Windows Job Object с KILL_ON_JOB_CLOSE и дополнительным пределом 4096 МиБ committed memory для рабочего дерева (это не RSS) предназначен для аварийной остановки. Конфигурация Job проверяется запросом ОС до допуска. Heartbeat содержит монотонное время, отправляется неблокирующей записью и не продлевается устаревшими сообщениями; зависший запрос телеметрии прерывает допуск через 2,5 секунды. Проверка датчика выполняется независимым контроллером, повторяется перед публикацией весов; избыточные блокирующие проверки на каждом окне убраны. Телеметрия отдельно печатается примерно раз в 5 секунд. Блокировка общая для экземпляров под одним Windows-пользователем, не для всех пользователей системы. При опасности не выполняется новая запись весов; используются последние сохранённые веса.

Checkpoint сохраняется раз в 25 шагов или 60 секунд (на ближайшей границе шага), при нормальном завершении также сохраняется остаток. Предыдущий корректный checkpoint хранится как `previous.uno` через жёсткую ссылку на неизменяемый старый файл, если файловая система это поддерживает (иначе проверенная копия); при повреждении основного контейнера проверяется резервный, повреждённый файл при RESUME сохраняется отдельно. Между сохранениями возможна потеря вычисленных шагов. Сохранение атомарное на уровне файлового API; устойчивость при отключении питания не доказана.

**Границы допуска:** эта версия проверена на Linux на синтетических тестах и коротких диагностических окнах реального корпуса. Аппаратный допуск в части тестовых сценариев моделировался, реальные показания не подменяются в штатной программе. Реальные Windows Job Object, CSV LibreHardwareMonitor, работа Acer при нагрузке и поведение Windows при аварии должны пройти CHECK и отдельный короткий контролируемый пилот. Программный мониторинг не является мгновенным аппаратным предохранителем и не доказывает, что сам датчик не возвращает замороженное значение. Порог 85 °C не менялся. Системные защиты, BIOS и драйверы не изменяются. Основное обучение не запускать до аппаратной приёмки.

## Математика и данные

Проверены применимые разделы 2, 3 и производные §6 оригинального математического кандидата Astra R5.4; исторические R5.3 и `UnoFReference` остаются источниками реализации: при пустом адресном чтении z=tanh(z0), а не z0. Сохраняются Us·s, z0, h0 и синхронный переход всех блоков. Слагаемые цели и metadata равны нулю в этом текстовом подрежиме. Адаптивный маршрут, адресное чтение, записи памяти и P не входят в вычислительный граф. По Astra 02/03 E служит и входным lookup, и общей выходной матрицей `logits = E h + b_text`. CE предсказывает следующий токен, включая EOS. Градиенты входа и выхода складываются в одном E. Градиенты через токены соседних окон отсекаются по TBPTT, численное состояние переносится. Состояние хранится в checkpoint, сбрасывается между отдельными документами корпуса. Каждый документ является фрагментом произведения, поэтому между раздельными фрагментами состояние также сбрасывается.

Хранятся только 514 активных строк E и b_text в порядке `active_ids`. Неактивные строки размерности V32768 подразумеваются нулевыми и исключены из softmax. Реализация хранит только параметры текстового подрежима и не выдаёт число параметров за полный инвентарь B2. Сохранены нормы A≤1, B≤0,9, C≤2, Us≤1, E≤8 (row L1), box1 для e/bz, box8 для других bias. FP32, Adam(.9,.999,eps 1e-8), clip L2=1, без weight decay. Новый кандидат FIX02: warmup 16 до 2e-4, плато до шага 1000, затем прежний cosine до 2e-5. Исходный режим сохранён через `--warmup 1000` (траектория LR совпадает на всех проверенных шагах). Выбор warmup фиксируется в checkpoint. Два потока по умолчанию — консервативный старт, а не доказанный оптимум Acer. Векторная L1-проекция использует ту же норму и строгую проверку; исходная реализация сохранена для сравнения и резервного вычисления. Перенос проекции из recovered TRAIN001 применяет FP64 вычисление порога и проверяет строгий запас на decoded FP32. FIX03 по умолчанию использует аналитический обратный проход для фиксированного окна: тот же переход, те же градиенты с допустимой FP32 погрешностью; веса обновляются тем же Adam. `--backend autograd` сохраняет исходный способ. Внешние производные между окнами по-прежнему отсечены; полная производная через весь документ не вычисляется. Сокращены повторные сканирования матриц, но каждый изменённый блок обязан пройти проверку decoded cap. Программа не претендует на полную приёмку R5.4.

Используется только проза `uno_b2/language/data.json`, split train для обновлений. Сцены из пьес отделены. Модель читает validation для явной команды TEST; holdout не подаётся в обучение и тест модели. CHECK проверяет целостность всей поставки, порядок BPE-слияний и каноническое повторное кодирование по одному полному фрагменту каждого из 23 произведений. TEST сравнивает модель со сбросом состояния, unigram и bigram на одинаковом префиксе validation. При `--validation-targets 112994` используется вся проза validation. Выводятся продолжение по собственным предыдущим токенам, доля соседних повторов и число замен невалидных UTF-8 байтов. Связность русского текста подлежит отдельной человеческой оценке после обучения.

## Формат весов

`--export text_f.uno` создаёт исследовательский контейнер `UNO-TEXT-F-FP32-1` с проверяемым SHA полезной нагрузки, безопасной загрузкой PyTorch `weights_only=True`, схемой `state_dict`, `active_ids`, хешем токенизатора, конфигом и номером шага. Имена: E[Vactive,d], Us[d,d], A/C[J,n,256,d], B[J,n,64,256], a[J,n,256], b[J,n,64], e/bz[d], b_text[Vactive]. `latest.uno` дополнительно содержит optimizer, RNG, курсор и состояние TBPTT. При загрузке до неявного преобразования PyTorch проверяются исходные типы и размеры тензоров, полная схема Adam, номер шага и RNG. Формат совместим с этой версией программы. Проверенный тестовый мост передаёт числа в существующий UnoFReference для сравнения перехода. Android-импортёр этого формата и языковой runtime ещё отсутствуют. Универсальный Kotlin-адаптер отображает E_text транспонированием в E[d,n] с иным ограничением строк, поэтому успешность прежнего ограниченного parity не означает допустимость всех будущих текстовых весов. Это отдельный открытый вопрос ABI, не повод изменять нормы текстового ядра. SHA проверяет целостность, не происхождение. Используйте собственные checkpoint.

Текущие результаты — `FIX03_EVIDENCE.md` и `evidence/fix03_*.txt`. Результаты FIX01/02 исторические; для их повтора нужна соответствующая исходная версия. Исследовательские скрипты FIX03 лежат в `evidence/fix03_repro/`, они не являются командами штатного обучения.
