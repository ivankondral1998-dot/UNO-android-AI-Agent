**Статус:** версия инструкции для исследовательской ветки; НЕ нормативная замена R5.3 и НЕ разрешение на production-код, обучение продукционных весов, GitHub Actions, Android OS-действия, утверждение G4/G5, merge или удаление. Сохранять исходные материалы без редактирования.

## Почему нужен этот документ

В предыдущих передачах пакетов UNO были смешаны понятия целостности архива и полноты научных первоисточников. Например, локальный ZIP на 349 записей проходит проверку CRC и SHA-256 своих 347 инвентарных файлов, но **не содержит** отдельного снимка всех 246 GitHub-файлов из исследовательской ветки, исходных `ASTRA_CURRENT/*`, `NORMATIVE/01..06`, `UNO_LAB_REPORTS.txt` и корпуса V01–V20 как файлов GitHub. Нельзя объявлять такой ZIP полным снимком проекта.

Подтверждённый на момент проверки источник: `ivankondral1998-dot/UNO-android-AI-Agent`, ветка `docs/uno-lab-research-handoff-20261105`, прежний HEAD до этой инструкции `28079d6460b3d709dd0f60e6afa449416e8343b3`, main `409f04bf95a0a3fec18934982d76be7285864f0a`. После любого коммита HEAD обязан быть перечитан; старый SHA остаётся лишь исторической контрольной точкой.

## I. Сначала устанавливать текущую реальность

1. Уточнить назначение пользователя и действующие разрешения, не спрашивая повторно уже установленное.
2. Для работы с репозиторием читать `AGENTS.md`, `README.md`, `docs/AGENT_START_HERE.md`, `docs/CURRENT_TASK.md`, `docs/STATUS.md` и актуальный SHA выбранной ветки.
3. Перед выводами по R5.3 читать `docs/precode/r5.3/source-package/00_START_HERE.md` → `NORMATIVE/01..06` → **полные** `SOURCES/ASTRA_CURRENT/ASTRA_00..12`, адресные R52/Grok и матрицы/gates. Короткий handoff не заменяет первоисточник.
4. Отмечать доступ каждого инструмента: `AVAILABLE`, `TESTED`, `BLOCKED`, `UNTESTED`. Не объявлять «все инструменты проверены», если проверялась только релевантная часть.

## II. Не смешивать проверки

- `ZIP_CRC_PASS`: данные читаются и CRC совпадают, НЕ доказательство полноты.
- `MANIFEST_SHA256_PASS`: присутствующие записи соответствуют самодекларированному манифесту, НЕ доказательство наличия всех требуемых файлов.
- `GIT_BLOB_SHA_PASS`: полученные байты соответствуют SHA указанного blob, НЕ свидетельство, что HEAD и дерево независимо подтверждены.
- `SOURCE_COVERAGE_PASS`: явный список **всех** обязательных источников совпадает с содержимым архива и проверен на пропуски.
- `SCIENTIFIC_EVIDENCE_PASS` и `DEVICE_VERIFIED`: отдельные проверки по независимым данным и устройству; не следуют из любой из файловых проверок.

Файл из Project/Library, доступный через `files.read`, может не иметь разрешённого пути выгрузки оригинальных байтов (`files.materialize`). Возврат текста, реконструкция исходника и побайтовый оригинал — разные уровни происхождения. Не маркировать reconstructed как original-byte-matched.

## III. Как готовить полный ZIP для Work

1. Сначала составить `REQUIRED_SOURCE_INVENTORY`: точные файлы R5.3/Astra, тесты V01–V20, LR-01/N0-01…N0-07, исходные логи, скрипты, закрытые решения и текущие инструкции.
2. Для автономной передачи получить Git-объекты точного, независимо подтверждённого коммита через авторизованный локальный checkout/cloud computer. Не смешивать `main` и исследовательскую ветку.
3. Размещать точную копию файлов дерева под `GITHUB_SOURCE_AT_PINNED_COMMIT/`, локальные доказательства отдельно под `LOCAL_EVIDENCE_AND_CONTEXT/`, отдельно хранить незаполненные пункты.
4. Составить манифест SHA-256 по каждому включённому файлу и SHA blob для Git-источников; проверить весь манифест, count и обязательные пути. Для контрольной точки 2026-11-06 дерево содержало **246 Git blob** суммарно **5 225 319 байт**; при новой контрольной точке счёт обновить.
5. Если нельзя скачать репозиторий полностью, **не заявлять «полный автономный ZIP»**. Выдать локальный пакет с статусом `PARTIAL_REPO_MISSING` и точным перечнем недостающих оригиналов. Не пытаться «исправить» это новой обёрткой ZIP над прежними ZIP.
6. Личную PMB-переписку не публиковать в GitHub; использовать отдельно как ограниченное контекстное свидетельство.

## IV. Как проверять работу и не зацикливаться

Для каждой существенной ошибки записать: `SYMPTOM`, `EVIDENCE`, `ROOT_CAUSE (confirmed/hypothesis)`, `CORRECTION`, `TEST`, `REMAINING_GAP`.

Если инструмент снова выдаёт тот же блокер без нового факта, прекратить идентичные вызовы. Попробовать другой путь только если он доступен и безопасен. Не заменять исполнение бесконечными обещаниями и отчётами.

Подтверждать отдельно `PLANNED`, `IMPLEMENTED`, `HOST_TESTED`, `ANDROID_BUILT`, `DEVICE_VERIFIED`, `RELEASE_READY`. Научные утверждения помечать `PROVEN_LOCAL`, `CONDITIONAL`, `SPECIFIED_UNTESTED`, `REQUIRES_DATA`, `OWNER_DECISION`, `FAIL` по реальным основаниям.

## V. Продуктовые ограничения UNO

UNO — единый полностью локальный нейронный организм; никакого незаявленного облачного ядра, независимых «мозгов», переноса старых весов Jarvis или подмены формулы F игрушечной классификацией. Наблюдение, объяснение владельца и проверенное Android-последствие — раздельные источники. Память/предсказание не дают разрешения; dispatch не доказывает успех; STOP не отменяет уже завершённый эффект ОС.

Текущая граница: `G4 PRECODE CANDIDATE`, `OWNER_APPROVED_PRECODE=FALSE`, `PRODUCTION_CODE_AUTHORIZED=FALSE`. Изолированные экспериментальные исследования допустимы только в отдельно разрешённых пределах. O01–O08 — решения владельца. Никаких удалений, main merge, force push, Actions без прямого разрешения.
